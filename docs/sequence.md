## Очередь после замены

Да, очередь остаётся неизменной. Замена меняет только `inspector_id` в конкретной записи `Schedule`. Генератор про это ничего не знает — он смотрит только на `ScheduleGeneratorState.last_user_id`.

```
Сгенерировано:
Пн М1 → U1,  М2 → U2,  М3 → U3,  М4 → U4,  М5 → U5
Пт М1 → U21, М2 → U22, М3 → U23, М4 → U24, М5 → U25

Замена: U1 (пн) ↔ U21 (пт)

В БД Schedule:
Пн М1 → U21  ← поменяли
Пт М1 → U1   ← поменяли

ScheduleGeneratorState.last_user_id = 25  ← не тронули
Следующая неделя начнётся с U26           ← как будто ничего не было
```

Очередь на будущее не ломается. Это правильное поведение.

## Что происходит с временным интервалом между проверками

Вот здесь интереснее. Возьмём пример.

```
Без замены:
U1:  Пн (неделя 1) → следующий раз Пн (неделя 4) = 15 дней
U21: Пт (неделя 1) → следующий раз Пт (неделя 4) = 15 дней

С заменой U1 ↔ U21:
U1:  Пт (неделя 1) → следующий раз Пн (неделя 4) = 10 дней  ← сократилось
U21: Пн (неделя 1) → следующий раз Пт (неделя 4) = 20 дней  ← увеличилось
```

То есть замена внутри одной недели меняет интервал до следующей проверки для обоих пользователей. Один ходит чаще чем положено, другой реже.

## Это проблема?

Зависит от требований. Есть два взгляда на это.

**Если замена — разовое исключение** и строгой равномерности не требуется, то это нормально. Система сама выровняется через несколько циклов.

**Если равномерность критична** — нужно при замене не просто менять `inspector_id`, а менять их местами в обеих записях. Что вы и делаете судя по описанию. Тогда суммарная нагрузка на двух пользователей сохраняется, просто перераспределяется между ними.

Уточните — у вас есть требование к строгому интервалу между проверками одного пользователя, или просто "примерно равномерно"?

**Если замена — разовое исключение** и строгой равномерности не требуется, то это нормально. Система сама выровняется через несколько циклов.
Вы точно уловили закономерность.

```
Без замены:
U1:  Пн → следующий Пн = 15 дней
U21: Пт → следующий Пт = 15 дней

Интервал между заменяемыми слотами = Пт - Пн = 4 дня

С заменой:
U1:  Пт → следующий Пн = 15 - 4 = 11 дней  ← сократилось на 4
U21: Пн → следующий Пт = 15 + 4 = 19 дней  ← увеличилось на 4
```

Формула простая — **отклонение = интервал между заменяемыми слотами**. Один получает `-N дней`, другой `+N дней`. Сумма отклонений всегда равна нулю, поэтому средняя нагрузка по всем пользователям не меняется.

Пн М1 → U1,  М2 → U2,  М3 → U3,  М4 → U4,  М5 → U5
Пт М1 → U21, М2 → U22, М3 → U23, М4 → U24, М5 → U25

2 неделя
по аналогии

3 неделя
по аналогии

В отпуск уходит U5 (допустим на 14 дней)
Мы в админке (График работы) под пользователем создадим кнопку "в отпуск. Удалить из расписания".
Администратор нажимает кнопку под U5. Модальное окно подтверждения. Администратор нажимает "да, удалить из расписания".
U5 удаляется из расписания в БД на эту дату. От этой даты и до конца сгенерированного расписания начинаем сдвиг.
На его место смещается U6 (заметь, что маршрут М1 U6 поменяется на М5 U5). На место U6 смещается U7 (маршрут также поменяется). И так далее.
Важное уточнение, если у какого то U поле is_swapped = True, то его пропускаем и не двигаем. Его нельзя сдвигать.
